# Tabframe

A fault-tolerant distributed computer whose cores are browser tabs and Firecracker microVMs,
programmed with WebAssembly. Open the page and your tab is a core. Close it and the machine keeps
computing, correctly. The control plane that schedules the work is itself replaced every hour, with
the work in flight.

Deployed: **https://d2w9z8juw4oo76.cloudfront.net** — the page lends one core when it opens, and
shows the machine rendering a Mandelbrot frame with whoever else is there.

## What it is

A program is one WebAssembly module with two entry points and a manifest. `plan` turns parameters
and the previous stage's outputs into the next stage's tasks; `run` turns one task's input into
bytes. Both execute on cores — the control plane runs no program code, not even the planner. A
program's only view of the world is a per-execution filesystem of content-addressed blobs: it has
no clock, no randomness, no network, and no failure type anywhere in its API.

Two programs ship with the machine and go through the same path as anything you write in the
in-page editor: a distributed **Mandelbrot** render (640 tiles of 64×64 per frame, presets that
advance while anyone watches) and a three-stage **word count** over *Moby-Dick* (map by byte range,
reduce by partition, merge to a top-25). You can also compile your own: the editor holds the
Mandelbrot source and the AssemblyScript compiler runs in a browser worker.

Since M6 a third program ships with the image: **tiny GPT**, an 822 k-parameter character-level
transformer trained on that same corpus, whose whole forward pass runs in WebAssembly on the cores —
one continuation per task, four milliseconds a token, the same bytes on every core
(`docs/feasibility-transformer.md`).

## 4. Nodes

A node is one orchestrator plus one sandbox plus one socket. Browser nodes run the orchestrator in a Web Worker and the sandbox in a nested worker. Cloud cores run the same orchestrator under Node with the sandbox on a worker thread. The control plane cannot tell them apart.

### 4.1 Lifecycle

1. **Boot.** The host (or the core's process) hands the orchestrator a session: endpoint, token, store base, generation.
2. **Hello** with protocol version, host id, core count, sandbox version. **Welcome** returns node id, heartbeat interval, in-flight limit, store base, generation. The node never chooses its id; the id is its address.
3. **Heartbeat** every second carrying raw signals only: visible flag, queue length, last task duration, tasks done. Nodes never label themselves fast or slow.
4. **Assign.** Up to two tasks in flight: one running, one queued, so the node never idles waiting for the next assignment.
5. **Compute** in the sandbox (§4.2). Output is deterministic bytes plus buffered file writes and a log.
6. **Upload then report.** The orchestrator asks for presigned URLs over its socket, uploads output, written files, and log to the store, collects the hashes the store vouches for, then sends `result` with hashes only.
7. **Cancel** drops a queued task or aborts a running one at the next opportunity; a result already on the wire is harmless.
8. **Commands:** `close` (the worker ends itself; the socket drops), `freeze` (stop heartbeating and computing, keep the socket open — the zombie the timeout path exists for; terminal), `throttle` (sleep between tasks, a tenth of the speed, heartbeats continue), `resume`.
9. **Death.** Tab closed, host called terminate, or `close` command — all identical to the control plane: the socket drops, nothing is sent first. A frozen zombie is caught by four seconds of silence. Once declared gone, the control plane closes the connection from its side so a zombie never lingers.
10. **Reconnect.** After an unexpected drop the orchestrator fetches a fresh session, reconnects with backoff, and says hello again as a brand-new node. Whatever it had in flight was released when the old node went silent.

### 4.2 Orchestrator and sandbox

**The orchestrator never runs program code.** On assign it ensures the program module is cached (fetch by hash, compile once, keep the compiled module), fetches the stage's filesystem manifest by root hash (cached), posts the compiled module, manifest, input, and limits to the sandbox, starts a deadline timer, and on expiry terminates the sandbox outright and spawns a fresh one — the only clean way to stop a spinning loop.

**The sandbox** instantiates a fresh WASM instance for every task, so no memory state leaks between tasks or programs. It binds the imports (§5.3) to glue closures:

- `stat`, `read`, `list` resolve a path against the stage manifest first and the task's own write buffer second; a resolved hash is fetched from the store with a synchronous request (allowed in dedicated workers; on Node, `Atomics.wait` against the orchestrator thread — both mechanisms verified in preflight on 2026-09-01), with a byte range when asked; a per-node cache by hash makes repeated reads free; unresolvable paths return an error to the program. There is no other network access, and the module cannot name a URL, only a path.
- `write` appends to an in-memory map from path to bytes, enforcing per-task caps on file count and total size; writing a path twice keeps the last.
- `log` appends to a capped buffer.
- A trap or abort ends the task with an error message instead of output.

The sandbox blocks during a synchronous read; heartbeats live in the orchestrator, so that is fine.

**Host ↔ orchestrator** talk only about status over postMessage: `init`, `visibility` inward; `status {nodeId, state: connecting|idle|busy|frozen|throttled|closed, tasksDone, lastTaskMs}` outward. Tasks and results never cross this boundary.

### 4.3 Cloud cores

Same image as the control plane; the run-hook payload selects `role=core` and carries the session URL. A core fetches a session, connects outward to the control plane endpoint on port 8080, and behaves exactly like a browser node. The control plane records each core's MicroVM id in the ledger, so the ids travel with the snapshot and a new control plane inherits its cores at adopt. Cores have no ingress connector, no idle policy, and a four-hour maximum duration as a cost fuse. The active control plane keeps two alive while the machine is awake (§6.8) and replaces one that dies, is killed by a demo control, or nears its ceiling. A cloud core killed by "kill half" reappears a few seconds later: self-healing, visible.

## Findings

`[H]` **control plane — packages/control-plane/src/server.ts:308 (also bundles.ts:34)** — every blob the control plane fetches on an untrusted party's say-so is pulled whole into memory with no size check: `store.get(e.hash)` for a plan task's stage spec, for an inherited root, and `resolveBundle`'s `store.get(bundle)` for a launch. `decodeStageSpec`'s 1 MB cap and `bundles.ts`'s module cap are applied *after* the download — and the manifest blob itself is never size-checked at all. Combined with the unbounded presign below, one anonymous message (`launch {bundle: <hash of a 1 GB blob>}`, or a node reporting that hash as its plan output) OOMs a 1 GB MicroVM and kills the whole machine; the successor adopts and the loop repeats. **Fix:** add `head(hash) → size` to `StoreDriver` and refuse before fetching (1 MB for a spec/manifest, `LIMITS.maxModuleBytes` for a module), or stream with a byte budget and abort past it.

`[H]` **store/presign — packages/protocol/src/observer.ts:24 and node.ts:64** — `size: z.number().int().positive()` has no upper bound, and `S3Store.presign` signs it as `ContentLength`. Any visitor (the endpoint token is vended by a public, unauthenticated Lambda URL) can subscribe and mint presigned PUTs for objects of any size and write them into the blob bucket, which keeps them a year; nothing counts bytes per connection. That is unbounded storage and egress cost against a $100 budget that is notification-only with no kill switch, and it supplies the giant blob the finding above needs. **Fix:** cap `size` at `LIMITS.maxOutputBytes` in the schema, and add a per-connection presigned-byte budget in `apply.ts` before emitting the `presign` effect.

`[H]` **sandbox — packages/sandbox/src/validate.ts:107-115** — `readMemoryLimits` returns on the **first** entry of the memory section, and `validateCompiled` never looks at memory limits, so the declared-maximum check only ever inspects memory 0. I built a module with two memories (memory 0: max 1 page — passes the cap; memory 1: no maximum — `export "memory"`), and it passed `validateModuleBytes(bytes, {memoryPagesMax: 1024})`; instantiating it and calling `memory.grow(4096)` succeeded, taking the exported memory from 1 page to 4097. Multi-memory is on by default in Node 22 and current Chrome, so an uploaded program grows to gigabytes on every visitor's tab and every cloud core, faster than the deadline kill. **Fix:** reject any module whose memory section declares more than one memory, and validate the limits of the memory actually exported as `memory` (or hand the instance a host-owned `WebAssembly.Memory` instead of letting it define its own).

`[M]` **control plane — packages/core/src/apply.ts:251** — every destructive control is unauthenticated: any visitor's observer socket may send `killHalf`, `freezeHalf`, `stop`, `restart`, `skip`, `killExecution`, throttled only by 5 msg/s and (for launches alone) 6/min. `killHalf` also terminates cloud-core MicroVMs (`executions.ts` `commandHalf`), which the fleet policy then relaunches against a 1-per-second `RunMicrovm` quota — a loop of kill/relaunch that both denies compute and burns money indefinitely. **Fix:** gate the destructive subset behind a capability the session function only issues to an operator (or a shared secret in the run payload), and add a global cooldown per control op.

`[M]` **hosting — packages/infra/lib/core-stack.ts:73 (+ absent everywhere)** — attacker-supplied blobs are served from the **same origin as the dashboard** (`https://<distribution>/blob/*`), and the distribution attaches no `ResponseHeadersPolicy`: no CSP, no `X-Content-Type-Options: nosniff`, no `Content-Disposition`. Anyone can upload arbitrary bytes (presign, above) and get a same-origin URL that the panels then render as a clickable link; a browser that sniffs `application/octet-stream` on navigation gives stored XSS on the dashboard origin, and any XSS there holds the shared endpoint token and full machine control. **Fix:** add a `ResponseHeadersPolicy` with a strict CSP for the page and `nosniff` + `Content-Disposition: attachment` for `blob/*`, or serve blobs from a separate domain.

`[M]` **wire — packages/core/src/apply.ts:185** — `result` and `presign` are exempt from the token bucket entirely (`const solicited = ...`), on the reasoning that `maxInFlight` paces them. It paces honest nodes only: a node that says hello and then sends `presign` with 300 items as fast as the socket allows costs nothing, and each item is an S3 `HeadObject` plus a signature (`s3.ts:57`). One connection turns into thousands of S3 calls a second from a 1 GB VM. **Fix:** give solicited messages their own bucket sized to `maxInFlight` × a small factor, and cap in-flight presign requests per node at one.

`[M]` **hosting — design §9.7, packages/protocol/src/limits.ts:12-13** — the binding limit is 16 concurrent connections per MicroVM endpoint, the ledger's caps are 256/64, and there is deliberately no per-IP limit. One client opening 16 sockets locks out every visitor *and* the fleet's own private port, so `/handover`, `/drain`, `/health` all fail and rotation degrades to the snapshot path. It costs an attacker nothing and the tokens are public. **Fix:** track connections per source address in the ledger and refuse past a small quota, reserve one slot for the fleet, and shorten `HANDSHAKE_TIMEOUT_MS` (currently 10 s) so unhandshaken sockets cannot hold slots.

`[M]` **control plane — packages/core/src/apply.ts:479, 519** — a ~100-byte `subscribe` makes the control plane re-serialize the whole task table, `canonicalStringify`-ing every row twice (once to measure, once to send) and emitting several 64 KB pages. Nothing rate-limits *connections*, so repeated connect → subscribe → drop churns CPU and the endpoint's 2 MB/s budget from one client. **Fix:** memoize the serialized snapshot per `meta.seq`, and count a subscribe against a per-connection/per-IP budget.

`[M]` **infra IAM — packages/infra/lib/image-stack.ts:89, fleet-stack.ts:41** — the control-plane and rotate roles get `RunMicrovm`/`TerminateMicrovm`/`GetMicrovm` on `anyImageArn` (`microvm-image:*`) with no tag or resource condition, though design §10.1 states the control plane may only manage "MicroVMs tagged as cores". A compromised control plane can therefore terminate the active control plane and every other MicroVM in the account, and launch VMs from any image, passing the core role. **Fix:** scope the resource to the tabframe image ARN and add a condition on the `project=tabframe` tag (and a `RequestTag` condition on `RunMicrovm`) so a core's role cannot reach control planes.

`[M]` **tooling — mise.toml:5-7** — `aws-cli`, `gh`, and `npm:aws-cdk` are pinned to `"latest"` on the path that runs `cdk deploy` under an **AdministratorAccess** identity, so a compromised release of any of them executes with full account rights; `bun.lock` is otherwise exact and CI uses `--frozen-lockfile`, which makes this the one unpinned link. Separately, `<email>` is copied verbatim into the shipped page (`packages/web/scripts/build.ts:75`). **Fix:** pin all three tool versions the way node and bun are pinned, and pin binaryen to a released version.

`[L]` **control plane — packages/control-plane/src/server.ts:544** — `fleetAuthorized` fails open (`if (!fleetSecret) return true`). Between boot and the `/run` hook the process holds no secret, so `/adopt` on the private port is unauthenticated and will turn a neutral process into a control plane holding an attacker-supplied ledger; the same is true for the whole local mode. Reaching port 8081 needs an AWS-minted token today, so this is depth, not a live hole. **Fix:** in `image` mode refuse `FLEET_ROUTES` outright until a secret is set, and require an explicit `TABFRAME_INSECURE_LOCAL=1` for the open local behaviour.

`[L]` **fleet — packages/control-plane/src/cores.ts:38** — the fleet secret is copied into every cloud core's run payload, though a core has no private routes to gate and runs untrusted WebAssembly all day. One escape or one process-memory read on a core yields the secret that authorizes `/handover`, `/adopt`, and `/drain` on every control plane. **Fix:** pass `fleetSecret: null` in `corePayload`, or derive a separate per-role secret.

## Summary

The security thinking here is unusually good for the shape of the system — content-addressed writes with a checksum pinned as a signed header, zod on every frame, one-way ledger metadata, a genuine least-privilege core role, no secrets or account identifiers in any tracked file (transcripts included; the scrubber and `whoami` guard hold up), and a dashboard that builds DOM with `textContent` throughout, so I found no XSS in the page's own code. The weakness is uniformly on the **resource** axis rather than the confidentiality axis: caps are declared in the protocol but not enforced at the points where an untrusted party's number reaches an allocation — presign size, control-plane blob fetches, the second WebAssembly memory. Fix, in order: bound every control-plane blob fetch by size before downloading it; cap `presign` sizes and charge them against a per-connection budget; and reject multi-memory modules so the declared memory maximum means what the design says it means.
